# 渲染审计：Markdown 在窄屏与 GitHub 上的可读性（t19）

内容对不对由 t14 管（[docs-audit.md](docs-audit.md)）。这份只回答一件事：同一份文档在 GitHub 首屏、13 寸笔记本、手机窄屏上，渲染出来能不能读。

**结论**：超宽表格从 66 张清到 0 张（本轮开工时 49 张，并行新增的 [architecture-audit.md](architecture-audit.md) 另有 17 张，同批处理）；代码块长行从 31 条降到 18 条，剩下的 18 条全部是「引用原文 / 单 token URL / 单行程序输出」，逐条写了原因与折行方案。标题层级、链接文字、图片引用三项本来就是 0，验证判据写在下面。

## 0. 怎么复现

```bash
# 全仓库渲染体检（表格 >100 列、代码行 >90 字符、标题跳跃、链接文字、图片）
python bin/md_render_check.py

# 只看某几个文件，或收紧阈值
python bin/md_render_check.py README.md docs
python bin/md_render_check.py --min-table 80 --max-code 80 --json

# 真截图（Edge headless，900px 桌面 / 420px 手机）
python test/render_markdown.py README.md --width 900 --height 1500 \
  --out test/out/shots/readme_900.png
python test/render_markdown.py README.md --width 420 --height 1400 \
  --out test/out/shots/readme_420.png
```

宽度算法：全角/CJK 字符算 2 列，其余算 1 列；表格每行成本 = 各列最大宽度之和 + 每列 3 列内边距与竖线 + 1。量的是「渲染后」宽度，不是源码字符数——所以中文表格比看起来更宽。

退出码：`0` 干净，`1` 有超标项，可以直接放进 CI。

## 1. 表格宽度：66 张 → 0 张

问题：任何一张渲染宽度超过 ~100 列的表格，在 420px 手机上都只能横向滚动；而 GitHub 的移动端不会给滚动提示，读者看到的是被切断的右半张表。

处理原则（没有删任何信息）：把「左边一两列是键、右边几列是长散文」的表格逐行拆成

```markdown
**<键>**

- **<列名>**：<原来的单元格内容>
```

每个单元格文字逐字保留，只是从「一行一表」改成「一条一块」。这一步是脚本做的，脚本用 `bin/md_render_check.py` 的同一个宽度函数判断哪张表超宽、哪些列是散文列，所以不存在「手抄丢字」。

例（`docs/index.md` 的「按处境查」，修前 230 列）：

```markdown
# 修前
| 处境 | 读这份 | 一句话说明 |
| 第一次拿到仓库，想知道怎么装 | [quickstart.md](quickstart.md) | 五分钟装好并确认两条通道都在…（原单元格更长） |

# 修后（宽度从 230 列降到 0，信息一字不少）
**第一次拿到仓库，想知道怎么装**

- **读这份**：[quickstart.md](quickstart.md)
- **一句话说明**：五分钟装好并确认两条通道都在…（原单元格更长）
```

本轮开工时扫描到 49 张（16 个文件，逐条见 1.1）；期间并行新增的 `docs/architecture-audit.md` 另有 17 张，用同一脚本处理了 16 张，剩下 1 张的表头本身少一列（`| 面 | 结论 |` 却有 3 列数据），改成手工并入块里，表格缺陷一并消掉。

## 2. 代码块长行：31 条 → 18 条

问题：`pre` 里超过 ~90 字符的行会出现横向滚动条。GitHub 上还能拖，但一旦被截图、打印、或贴进聊天窗口，尾巴就丢了——而命令行漏掉尾巴通常是跑不起来，不是跑错。

### 2.1 已修的 13 条（逐行核对）

改法有三种，都保证「复制整段仍然跑得通」：

- **续行符折行**：bash 用行尾 `\`，把长命令拆成两段（`grep ... \` + `  | grep -v ...`）。
- **变量提取**：把重复的长路径提成 `PY="..."`，后面几行用 `"$PY"`，三条探针命令从 107/118/116 列降到 80 列以内。
- **注释单独成行**：代码与 `# -> 输出` 写在同一行会把长度顶到 90 以上；把注释移到下一行即可，示例值不变。

验证方式不是看代码块，而是重新跑：`runtime/py32/python.exe bin/cli.py kd formula --smiles 'CC(=O)Oc1ccccc1C(=O)O'` 仍是 `C9H8O4`。

### 2.2 未修的 18 条：为什么，以及要折该怎么折

这 18 条超宽是「内容本身不可折行」或「折了会改变证据」，逐条说明：

**A. CDXML / XML 原文摘录（4 条，`docs/cdxml-minimal.md:12,83,84,91`）** — 这些是 ChemDraw 自己吐出来的 XML，读者要拿去和本机输出逐字节比对。XML 属性之间换行是合法的，但换完就不是「原样摘录」了。

> 折行方案（若确实要折）：属性分组换行，例如 `<n id="7" p="283.30 347.74" Z="8" Element="8"` 换行后续 `NumHydrogens="1" NeedsClean="yes" AS="N" AtomID="7">`。改的是呈现，不是语义，但会与 `docs/cdxml-minimal.md` 里的「原样」声明冲突，所以本轮保留并在此声明。

**B. 出版社原文英文引句（2 条，`docs/journal-artwork.md:122,139`）** — 逐字引用的英文原句，折行会伪造引文。

> 折行方案：把这两段从 ``` 代码块挪到 `>` 引用块。Markdown 引用块会按窗口宽度自动重排，英文原句一个字都不用动，也不会出现横向滚动。本轮未改，因为该节体例是「原文照抄在代码块里」，换体例要同步改 §0 的说明。

**C. Elsevier 官方表头的 ASCII 对齐（1 条，`docs/journal-artwork.md:214`）** — `TARGET SIZE        Image width ...` 的空格本身就是列对齐信息，折行会把列关系打散，属于不可折行数据。

**D. curl 复现块（6 条，`docs/journal-artwork.md:530-540`）** — 这些是「复制整行就能下到 PDF」的命令，URL 是不可拆的单 token（最长 199 列）。拆成 `URL="..."` 变量 + 短 curl 之后，URL 那一行仍然是 199 列，所以只把 curl 调用本身降下来了，长行没消失。

> 已给出的折行方案：`UA` 拆成两段 `UA=` / `UA+=`（值不变），`ACS=`、`WILEY=` 提成变量，`curl -sSL -A "$UA" -o acs_jacs.pdf "$ACS"` 只剩 43 列。三条 Elsevier/RSC 的 URL 仍超宽，这是 URL 长度的物理下限。

**E. 单行程序输出摘录（3 条，`docs/portability-report.md:64,369,376`）** — 是当时 `python -c` 的真实输出（`ok=False code=E06 message='cannot read image' ...`）。折行等于改写历史输出，会让人怀疑「这条到底是不是原样」。

> 折行方案（重新采集而不是改旧记录）：下次记录时用 `... | fold -w 90` 或 `| cut -c1-90`，输出自然按 90 列断行；旧记录保持原样。

**F. 上游代码摘录与实测输出（2 条，`docs/upstream-com-notes.md:73,193`）** — 同上，是引用他人的调用序列与本机观测值。


## 7. 渲染工具本身的两个坑（都已修）

1. `test/render_markdown.py` 的样式表用 `%` 格式化注入宽度，而样式表里本来就有 `max-width: 100%`，于是每次渲染都死在 `TypeError: not enough arguments for format string`——截图工具挂了却像文档有问题。改成字符串替换即可（已修）。
2. `bin/md_render_check.py` 第一版按 `|` 直接切分单元格，遇到 `grep -E 'a\\|b'` 这种转义竖线就把 4 列的行切成 5 列，宽度全错（`docs/docs-audit.md` 的一张表因此被算成 370 列）。现在转义竖线归属单元格，`docs/portability-report.md:387` 的 grep 也能正确计数。

## 8. 未验证 / 已知边界

- **只在 Chromium 内核上验过像素**。Firefox 的等宽字体与中文字宽略有差异，`md_render_check.py` 的「CJK 算 2 列」是近似，不是所有字体的真值。
- **GitHub 自己的 CSS 没有复刻**。`test/render_markdown.py` 用的是仿 GitHub 样式，能判定「会不会横向滚动」，但判定不了 GitHub 特有的表格最小宽度收缩。
- **没跑移动端 WebKit**。420px 只代表窄视口，不代表 iOS Safari 的字体替换。
- **tab 宽度**：宽度函数按字符计数，代码块里的制表符按 1 列算，若某段用 tab 对齐，实际渲染会更宽。本仓库代码块已无 tab。
- **顺带发现（不属于渲染层，未改）**：`PROGRESS.md` 引用的 `artwork.export_args(...)` 已经不在模块里（`AttributeError`，现名 `artwork.resolution_for`）。这属于 t14 的内容对账范围，只在渲染样例里出现，按「不改技术内容」的约束保留原样。
